# Company profile and metric contract

The company profile is Markdown at `companies/{company_id}/profile.md` in S3. It contains general company context. ESB is the only component that accesses S3, PostgreSQL, and ClickHouse.

## Metric settings

PostgreSQL is the source of truth for structured settings. Each row stores:

- `metric_id`: opaque UUID generated by PostgreSQL for this company row. Valera never creates or encodes this ID.
- `company_id`: UUID of the company.
- `type_code`: catalog word: `ставка`, `депозит`, `курс`, `логистика`, `цена`, `спрос`, `запас`, `контрагент`, or `зарплата`.
- `name`, `description`, `metric_type`, `characteristic`, `unit`, and structured `parameters`.

At most one row per `(company_id, type_code)` is stored. The metric type is the PostgreSQL `company_metric_type` enum. Current Valera catalog rows use `metric_type: score` and an empty unit. Other metric types can retain a concise measurement unit such as `₽`, `%`, `шт.`, `тонн/месяц`, or `USD/баррель`; PostgreSQL is the source of truth for that unit. `parameters.source_fields` contains the exact input field names that triggered the row. Do not include source field values.

The type order is `ставка`, `депозит`, `курс`, `логистика`, `цена`, `спрос`, `запас`, `контрагент`, `зарплата`. Unknown type codes are preserved and sorted after these values; Valera must use the nine catalog codes above.

## Profile save and retry

`profile_revision` is a positive, monotonically increasing revision supplied by Domain. `save_company_profile_and_metrics` takes the complete Markdown profile and complete metric snapshot for that revision. ESB atomically replaces the metric settings in PostgreSQL, then writes the stable S3 profile key. Omitted metric rows are removed; an empty array removes all rows. An older revision cannot overwrite newer data. Repeating the same revision and payload is idempotent, including repair after a partial S3 failure.

Valera makes one call to `save_company_profile_and_metrics`. On a transient failure, retry once with the exact same company ID, revision, Markdown, and metric settings. Do not invent IDs or increment the revision for a retry.

## Analytics boundary

ClickHouse stores news, company-independent facts, fact-to-company links, observations, and generated analyses. An observation carries the PostgreSQL-generated `metric_id`; the `metric_id` is opaque and must not encode or reveal a type or company. News owns the publication time, URL, and source kind used by analytics. Totals are computed when requested and are not stored in ClickHouse.

Valera uses the following rules from the company input:

- **ставка**: `hasLoans`, `hasLeasing`, `hasGuarantees`, or `hasFactoring` is true.
- **депозит**: `hasDeposits` is true.
- **курс**: `ftsCountryName` is non-empty.
- **логистика**: `ftsCountryName` is non-empty, or activity group is trade, construction, production, or transport.
- **цена**: activity group is trade, construction, production, or energy.
- **спрос**: `mainOkvedCode` is non-empty.
- **запас**: activity group is trade, construction, or production.
- **контрагент**: external-payment data is present; record the exact source field name from the input in `parameters.source_fields`.
- **зарплата**: `hasPayroll` is true, or employee count is present and not `менее 15`.

These are configuration triggers, not calculation rules. Valera does not create a metric row merely because a value appears in revenue. See the skill's catalog and examples for company-specific characteristics.

The Domain request to `POST /call?agent=valera` uses `companyId`, `profileRevision`, and `company`. ESB normalizes it before invoking Hermes as `company_id`, `company_data`, and `profile_revision`.
