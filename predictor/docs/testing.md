# Тестирование ESB

## Уровни

| Уровень | Команда | Что проверяется |
| --- | --- | --- |
| Unit | `make test-unit` | Доменные правила, валидация application-сценариев, нормализация данных, ретраи и частичные ошибки адаптеров на `httptest` и фейках. |
| Integration / E2E | `make test-e2e` или alias `make test-integration` | Внешние HTTP, WebSocket и MCP контракты и взаимодействие с PostgreSQL, ClickHouse и MinIO через ESB. Два ESB процесса используют общий PostgreSQL; два Hermes mock экземпляра проверяют лимиты и маршрутизацию. |
| Real LLM / MCP | `make test-llm-tools` | Opt-in прогон Савелия, Кеши и Константина через Hermes, ESB и изолированные хранилища; проверяется фактический вызов `get_company_profile` моделью. |
| Full suite | `make test` | Unit-набор, затем изолированный integration/E2E стенд. |
| Race | `make test-race` | Go unit-тесты с `-race`; внешний Compose-набор запускается отдельно командой `make test-e2e`. |
| Coverage | `make coverage` | Coverage Go unit-тестов ESB: строки по пакетам и общий итог в текстовом выводе. |
| MCP security | `make test` / `make test-e2e` | Раздельные токены, закрепление сессии за ролью, call-scoped company context, параллельное чтение разных компаний, отказ подмене scope и безопасная проверка evidence Константина. |

Отдельного integration-набора для прямых вызовов репозиториев нет: сценарии с семантикой PostgreSQL, ClickHouse и S3 проходят через публичные интерфейсы ESB. Поэтому `test-integration` оставлен alias для E2E набора, который поднимает эти изолированные сервисы. Mock-набор не использует LLM credentials. Real LLM тест запускается отдельно и использует только локальный `LLM_API_KEY` из `predictor/.env` или окружения.

Все `*_test.go` находятся в `predictor/tests/`. Unit-тесты компилируются с пакетами ESB через overlay; E2E-модуль не подхватывает их повторно.

## Требования к E2E

Нужны Docker Engine с работающим daemon и Docker Compose v2. `make test-e2e` проверяет оба требования до запуска; если Docker недоступен, команда завершается с сообщением о требуемом компоненте. Compose-файл `predictor/tests/compose.e2e.yml` создаёт отдельные контейнеры и volumes для PostgreSQL, ClickHouse, MinIO, mock Hermes и ESB. Скрипт применяет init-миграции, ждёт health checks и удаляет контейнеры, сеть и volumes при завершении.

Если обычный E2E прогон завершился ошибкой, скрипт печатает логи только тестового Compose-проекта перед очисткой. Внутри fixture используются синтетические IDs и credentials. Не помещайте клиентские данные или реальные ключи в фикстуры и диагностические логи.

## Реальный вызов MCP через Hermes

`make test-llm-tools` использует отдельный Compose project и временные PostgreSQL, ClickHouse и MinIO. Проверка пропускается, если `LLM_API_KEY` не найден. Она запускает не более четырёх реальных LLM runs: один для Савелия, один для Кеши, один первичный анализ Константина и один вопрос через его WebSocket. Для каждого синтетического источника ESB также получает `POST /call?agent=serezha` через mock Hermes, чтобы создать company-source запись PostgreSQL, которую проверяет Константин при сохранении цитат. Для ESB submission retries установлено `1`; тестовые `max_turns` ограничены 8 для Савелия и Кеши/Константина.

Hermes направляет MCP-запросы через тестовый прозрачный proxy к ESB. Proxy сохраняет только `tool`, `agent` и синтетический `correlation_id`; аргументы, заголовки, ответы инструментов и тексты модели не записываются. Проверяются фактический `get_company_profile` от модели, его порядок перед сохранением результата там, где агент пишет данные, завершение вызова и ожидаемая запись/ответ. Константин проходит начальный анализ и вопрос через WebSocket; тест сверяет точный `source_id` синтетической новости в evidence обоих ответов и проверяет сохранённую историю. Реальные ответы могут быть недетерминированными: отсутствие точной цитаты оставляет eval красным и требует ручной проверки ответа и источников. Этот smoke test не доказывает устойчивость модели к любым prompt injection. При ошибке скрипт не печатает контейнерные логи и удаляет только volumes собственного Compose project.

## Coverage

`make coverage` использует `go test -coverprofile` и `go tool cover` из установленного Go toolchain. Вывод содержит coverage для каждого Go-пакета ESB и итоговый процент. Временный профиль хранится в системном temp-каталоге только на время команды и удаляется после печати отчёта.

Сетевой E2E-клиент обращается к отдельному ESB-процессу в контейнере. Этот бинарник не собран с Go coverage-инструментированием, поэтому E2E подтверждает поведение, но не увеличивает проценты `make coverage`. Автоматический порог процента не установлен: важнее покрыть ошибки, повторы, границы данных и восстановление после частичного сбоя.

## Приоритетные сценарии

- terminal/non-terminal статусы и допустимые типы метрик;
- идентификаторы и периоды фактов, страничные курсоры и ограничение неограниченных запросов;
- принадлежность metric ID компании, finite значения наблюдений и измерительная единица из PostgreSQL;
- повторная синхронизация профиля после частичной ошибки S3/PostgreSQL;
- восемь одновременных одинаковых POST-запросов с одним ключом идемпотентности возвращают один PostgreSQL вызов;
- ошибки авторизации, некорректный JSON, превышение размера тела и обезличенный ответ о недоступной зависимости;
- таймауты и отмена запросов к Hermes и ClickHouse;
- ограниченные/повторные HTTP-операции S3, ClickHouse и Hermes через `httptest`;
- HTTP, WebSocket и MCP через ESB, повторная обработка, история Константина и безопасная очистка в E2E Compose-стенде.
- Ответ Константина с рассуждениями перед итоговым JSON: в WebSocket попадает только `text` и серверные источники; без итогового JSON возвращается безопасное сообщение.
- Резервирование Hermes runtime между двумя ESB-процессами: четыре одновременных вызова при ёмкости двух экземпляров по два, пятый остаётся в очереди и запускается после освобождения слота.
- Фактические MCP tool calls через Hermes проверяются только `make test-llm-tools`; обычный mock E2E доказывает маршрутизацию, но не вызовы модели.
- Mock E2E заставляет mock Hermes вызвать `get_consultant_context` через MCP ESB в рамках конкретного `/call` и проверяет сохранение scope и evidence. Это проверяет границу ESB, но не подтверждает, что реальная модель сама выберет инструмент; такую проверку выполняет только opt-in `make test-llm-tools`.
- E2E также проверяет отклонение пустого `evidence`, выдуманного ID, источника другой компании и источника, который не вернулся из MCP-контекста текущего вызова. Все невалидные случаи сохраняются как безопасное сообщение с пустым списком ссылок.

## Надёжность тестов

Для синхронизации используйте каналы и сигналы готовности; не используйте `time.Sleep`. Даты задавайте явно, JSON/map-порядок не считайте контрактом. На каждом тестовом HTTP-сервере регистрируйте `defer server.Close()`. Для фоновых горутин задавайте владельца, остановку и bounded timeout. Не проверяйте текст динамических ошибок драйверов; проверяйте тип/`errors.Is`, безопасный внешний статус и отсутствие утечки payload/credentials.
