# Интеграция Domain ↔ ESB

Машинные схемы: [OpenAPI](api/openapi.json), [AsyncAPI для WebSocket](api/asyncapi.json), [MCP-инструменты](api/mcp-tools.md) и их [JSON Schema](api/mcp-tools.json).

## Подключение

Адрес ESB задаётся `HTTP_ADDR` (по умолчанию `http://localhost:8081`). `/readyz`, `/call` и WebSocket `/stream` требуют `Authorization: Bearer <ESB_API_KEY>`. MCP `/mcp` принимает отдельный Bearer-токен агента: `MCP_TOKEN_SEREZHA`, `MCP_TOKEN_SAVELIY`, `MCP_TOKEN_VALERA`, `MCP_TOKEN_KESHA` или `MCP_TOKEN_KONSTANTIN`. Токен Domain не авторизует MCP. Открыт только `GET /healthz`.

| Запрос | Назначение |
| --- | --- |
| `POST /call?agent=<type>` | Асинхронно запустить агента. `202 Accepted` возвращает `call_id`. |
| `GET /call?agent=<type>` | Прочитать вызов по `call_id`, отчёт Кеши или состояние/историю Константина по `companyId`. |
| `GET /call?data=facts` | Читать факты из ClickHouse; фильтры и курсор передаются JSON-телом GET. |
| `GET /stream?...` | Единственный WebSocket ESB — поток Константина. URL подписки возвращает `GET /call?agent=konstantin`. |
| `POST /mcp` | Streamable HTTP MCP endpoint для Hermes; инструменты публикуются через `tools/list`. |

ESB определяет MCP-роль по Bearer-токену и привязывает к ней созданную MCP-сессию. Серверный allowlist действует для `tools/list` и прямого `tools/call`. Декларация `mcp_tools` в `agents/<type>/agent.json` сверяется со встроенной политикой при старте ESB. Подмена query-параметра `agent`, аргумента модели или состава Hermes `tools.include` не повышает права. Токены должны быть уникальными, содержать 32–256 байт и отличаться от других ключей; генерируйте каждый независимо, например `openssl rand -hex 32`, и храните только в игнорируемом `predictor/.env`.

В текущем контракте `GET /call` использует JSON-тело. Некоторые клиенты и прокси его отбрасывают; проверьте это на используемом HTTP-клиенте. Переводите `http(s)` в `ws(s)` при подключении к возвращённому относительному `streamUrl`.

## Запуск агентов

Для любого POST выбирайте агента только query-параметром и передавайте данные JSON-телом. В таблице перечислены минимальные поля; полные wire-схемы находятся в [OpenAPI](api/openapi.json), `agent.json` задаёт scope и обязательные поля агента, а skill — его роль и порядок работы.

| `agent` | Основные поля тела | Задача |
| --- | --- | --- |
| `serezha` | `news_id`, `source_id`, `news_text`; метаданные новости — по возможности | Сохранить новость и извлечь универсальные факты. `news_text` — очищенный текст до 1 МиБ; если передан `company_id`, обязателен `source_url`. |
| `saveliy` | `company_id`, `news_id`; `facts` можно передать сразу | Связать существующие универсальные факты с компанией. |
| `valera` | `companyId`, `profileRevision`, `company` | Обновить Markdown-профиль в S3 и полный снимок настроек метрик в PostgreSQL. |
| `kesha` | `company_id`; для анализа периода — `period_from`, `period_to` | Рассчитать предикты метрик и сохранить аналитические результаты. |
| `konstantin` | `companyId` | Запустить анализ компании; для чтения анализа, истории и адреса подписки используйте GET ниже. |

Пример постановки новости:

```http
POST /call?agent=serezha
Authorization: Bearer <ESB_API_KEY>
Content-Type: application/json
```

```json
{
  "news_id": "news-123",
  "source_id": "22222222-2222-4222-8222-222222222222",
  "company_id": "11111111-1111-4111-8111-111111111111",
  "source_url": "https://example.org/news/123",
  "material_kind": "external_news",
  "media_type": "text/html",
  "published_at": "2026-10-25T09:00:00Z",
  "news_text": "Очищенный текст новости."
}
```

Ответ — `202 Accepted` с `call_id`. Для статуса или результата передайте его в теле `GET /call?agent=serezha`: `{"call_id":"..."}`. Для Валеры ответ также содержит `call_id`; используйте это же snake_case-поле при чтении статуса. Повтор одинакового `source_id` или пары `companyId` + `profileRevision` безопасен; тот же ключ с другими данными конфликтует.

Пример запроса Валеры принимает как плоский объект, так и контрактную обёртку `payload`:

```json
{
  "payload": {
    "companyId": "11111111-1111-4111-8111-111111111111",
    "profileRevision": 2,
    "company": { "orgType": "КОММ_ОРГ", "hasLeasing": true }
  }
}
```

В проде `company` должен содержать весь снимок Domain. Ответ `202` означает, что задача принята; завершение Валеры считается успешным только после подтверждения записи профиля в S3 и настроек метрик в PostgreSQL.

## Факты

`GET /call?data=facts` принимает фильтры `companyId`, `newsId`, `sourceId`, `materialKind`, `category`, `entity`, `periodFrom`, `periodTo`, `limit` и `beforeFactId`. Идентификаторы компании и источника — UUID; `newsId` — стабильный ID новости. Можно комбинировать фильтры.

```json
{
  "companyId": "11111111-1111-4111-8111-111111111111",
  "sourceId": "22222222-2222-4222-8222-222222222222",
  "materialKind": "external_news",
  "periodFrom": "2026-10-01T00:00:00Z",
  "periodTo": "2026-10-26T00:00:00Z",
  "limit": 100
}
```

`periodFrom` включается, `periodTo` исключается; вместе они задают окно не длиннее 90 дней. Нужен хотя бы один ограничивающий фильтр: компания, новость, источник или период. Без `companyId` выдаются универсальные факты; с `companyId` — факты, уже связанные с компанией, вместе с релевантностью. Размер страницы по умолчанию и максимум — 100. Если `hasMore` равен `true`, передайте `nextBeforeFactId` как `beforeFactId` следующей страницы.

## Метрики и отчёты

Валера записывает настройки компании полным снимком в PostgreSQL. Каталожные `type_code`: `ставка`, `депозит`, `курс`, `логистика`, `цена`, `спрос`, `запас`, `контрагент`, `зарплата`. PostgreSQL создаёт непрозрачный UUID `metric_id`; характеристики и параметры остаются только в PostgreSQL. Hermes получает чтение и запись настроек через MCP ESB.

`save_metric_observations` сохраняет в ClickHouse наблюдения с `company_id`, `metric_id`, `news_id`, nullable `value` и `probability`, а также `source_fact_ids`. Период к наблюдению не относится: расчёт фильтрует по `published_at` связанной новости.

`calculate_metric_total` принимает `metric_id`, `period_from`, `period_to`; границы включаются. ESB определяет компанию метрики через PostgreSQL, рассчитывает результат по ClickHouse наблюдениям и сохраняет его снимок в ClickHouse. Поддерживаются `YYYY-MM-DD HH:mm:ss`, RFC 3339 и даты `YYYY-MM-DD` (дата в `period_to` означает конец суток). `total_value` — арифметическое среднее ненулевых значений, без весов по вероятности; ноль учитывается. `total_probability` — отдельное среднее известных вероятностей среди тех же наблюдений с ненулевым значением. Новость без времени или отсутствующая новость исключается. Каждое наблюдение учитывается отдельно; ссылки на новости уникальны и сортируются по времени и `news_id`.

`fact_count` — число выбранных наблюдений, а не число уникальных `source_fact_ids`; `probability_count` — число этих наблюдений с известной вероятностью. При пустой выборке оба средних равны `null`, счётчики равны нулю, `links` пуст. При каждом расчёте ESB сохраняет актуальный снимок в `metric_totals` по ключу компании, метрики и периода. `calculate_all_metric_totals` читает настройки компании из PostgreSQL, сохраняет и возвращает по одной строке на настройку в порядке каталога, включая строки без наблюдений.

## Константин: GET, история и WebSocket

Для явного запуска анализа используйте `POST /call?agent=konstantin` с телом `{"companyId":"..."}`. Затем запросите `GET /call?agent=konstantin` с тем же телом. Если актуальный анализ готов, ответ `200` содержит его полный текст, `evidence`, `streamUrl` и страницу истории. Если анализ отсутствует или устарел, GET сам ставит его в очередь и возвращает `202` со статусом `processing`, `requestId`, `streamUrl` и той же ограниченной страницей истории. Анализ устаревает при новой ревизии профиля или нового материала компании.

История берётся из PostgreSQL порциями. В запросе доступны `historyFrom`, `historyTo`, `historyLimit`, `beforeMessageId`; период задаётся RFC 3339, начало включается, конец исключается. По умолчанию возвращаются последние 30 дней, максимум за один запрос — 100 сообщений и 90 дней. Ответ включает `historyHasMore` и `historyNextBeforeMessageId`; передайте последний курсор как `beforeMessageId`, сохраняя тот же временной диапазон.

Подключитесь к `streamUrl` с bearer-токеном. Поток `/stream` предназначен только для Константина и не принимает `agent`. Он отправляет сохранённые события; для возобновления после разрыва передайте `afterMessageId`. Вопрос отправляется JSON-кадром `kind: "question"` с уникальными UUID `requestId` и текущими `analysisId`, а также `text` до 1 МиБ. ESB отправляет подтверждение `accepted`, затем полный кадр `assistant_answer`; исходный анализ приходит как `analysis_result`. Перед отправкой кадра ответ и доказательства записываются в PostgreSQL.

## Совместимость и повторы

Настройки Валеры — полный снимок. Повтор той же пары `(companyId, profileRevision)` безопасен; более старая ревизия отклоняется. Повтор при частичном сбое восстанавливает синхронизацию S3 и PostgreSQL; если после автоматического повтора Валера не подтвердил запись, вызов получает статус `failed`.

`POST /call?agent=serezha` принимает текст новости до 1 МиБ и идемпотентен по `source_id`. Метаданные компании и источника нужны для привязки материала и актуальности анализа Константина. Для просмотра статуса всегда передавайте `call_id` вместе с тем же `agent`.

После статуса Hermes `completed` ESB проверяет ClickHouse marker обработки, хеш, метаданные и число фактов. Только после подтверждения он сохраняет хеш вместо сырого текста в завершённом вызове PostgreSQL. Текст новости остаётся в `news_content` до истечения `CLEANUP_PROCESSED_NEWS_TEXT_RETENTION`, отсчитываемого от подтверждённой обработки. Сбой до подтверждения оставляет исходный текст в ClickHouse и retry payload в PostgreSQL. Удаление текста не удаляет метаданные, факты, связи, наблюдения, итоги или анализ.

Очистка ESB имеет отдельный цикл сверки зависших вызовов (`CLEANUP_STATUS_CHECK_INTERVAL`) и цикл retention (`CLEANUP_RETENTION_CHECK_INTERVAL`). Сверка проверяет Hermes только для старых активных вызовов; ошибки запроса и ответ `unknown` оставляют вызов активным. Подтверждённые `failed`/`interrupted` вызовы повторяются только в пределах `CLEANUP_ACTIVE_MAX_RETRIES`. Подтверждённо зависшие отправки без `hermes_run_id` возвращаются в очередь с прежним ключом идемпотентности.

`CLEANUP_*_RETENTION` задают отдельные сроки для payload и записей вызовов, резюме, сообщений каждого агента и каждой категории ClickHouse. Используйте Go duration (`168h`), `never` или `0`/`0s`/`immediate` для очистки сразу после завершения и проверки зависимостей. По умолчанию история Константина, резюме, метаданные и аналитические категории хранятся бессрочно. Метаданные, на которые ссылаются сохранённые факты или наблюдения, остаются, пока эти зависимости существуют; факты — пока на них ссылаются связи с компаниями или наблюдения. Необработанный текст в ClickHouse можно очищать только для терминального вызова Серёжи, а соответствующий PostgreSQL payload сохраняется до подтверждённой обработки, чтобы повтор не потерял исходные данные. `CLEANUP_BATCH_SIZE` ограничивает одну пачку по каждой категории. PostgreSQL advisory lock не допускает конкурентных проходов на нескольких экземплярах ESB; ClickHouse mutation ожидается и проверяется через `FINAL`.

`context_policy` в `agents/<type>/agent.json` управляет историей, которую ESB передаёт Hermes, и сжатием контекста. Полная история PostgreSQL очищается независимо через `CLEANUP_MESSAGES_RETENTION_<TYPE>`; резюме — через `CLEANUP_CONTEXT_SUMMARY_RETENTION`. Обе политики по умолчанию `never`, поэтому Domain продолжает получать историю Константина порциями.
